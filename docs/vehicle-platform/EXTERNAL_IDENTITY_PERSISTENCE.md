# External Identity Persistence — Phase 1B Decision Record

**Status: architecture decision, implemented in shadow mode.** This document records the Phase 1B
persistence decision for external-identity bindings. It is fixed by architecture review, not open
for re-litigation as an implementation-choice debate in this or a future packet — see
`MIGRATION_PLAN.md`'s Phase 1 section for how this fits the overall sequence, and
`status/CURRENT.md` for exactly what is and is not consumed yet.

This document assumes familiarity with `EXTERNAL_IDENTITY_CONTRACT.md` (Phase 1A's observational
vocabulary — namespace, entity type, mapping state, trust level) and `CURRENT_STATE.md` §10
(Mechanism A / Mechanism B structural description). It does not repeat that material.

None of the four owners is removed, disabled, or changed in behavior by this packet. This is
purely an *addition* — a new, currently-unconsumed source of truth for exactly one narrow class of
fact: pinned identity decisions.

### A. Git canonical registry owns: pinned, non-reconstructible external identity decisions

New in Phase 1B: `automotive/vehicle_master/integration_data/external_identity_registry.json`,
loaded/validated by `tdr_bridge/external_identity_registry.py`. A binding belongs here only if it
is an actual identity **decision** — something that could not be regenerated by rerunning a
release build, a name/alias match, or a serving publisher. It receives ordinary Git review/audit
semantics, exactly like the rest of canonical Vehicle Master truth (`vehreg/data/`): a change is a
diff, reviewed and merged like any other canonical edit.

### B. Mechanism A owns: no canonical binding truth, only derived read-side mappings

`tdr_bridge/release.py`'s release-build crosswalk (`_brand_crosswalk`/`_model_crosswalk`) continues
exactly as before. Its 383 Brand+Model links (as of the 2026-09-15 baselines) are **not**
bulk-imported into the registry, and never will be merely because they agree with a canonical
name, alias, or an `integration_data/crosswalk_overrides.json` entry — agreement with a
deterministic match is not a pinned decision. See "Why agreement is not enough" below.

### C. Supabase `canonical_object_map` owns: operational migration/review/compatibility state

`canonical_object_map` is unchanged, untouched, and remains load-bearing in existing production
paths: the Phase-C write-authority gate (`lib/canonical-write-shadow.ts`), `unmatched`/`ambiguous`
review-state tracking, and Phase-E serving-projection bookkeeping (§D below). It is **not** chosen
as the long-term canonical source of truth for pinned bindings — but it is not retired, migrated,
or behaviorally altered either. No Supabase migration occurs in Phase 1B.

### D. Phase-E serving projection owns: generated, reconstructible child mappings

`apply_vehicle_serving_projection` (`supabase/migration_v14_serving_projection.sql`) writes
`canonical_object_map` rows every time it projects a legacy child row from canonical state — see
"Phase-E verification finding" below for exactly what this code does. These rows are operationally
authoritative *for that projection* and fully reconstructible by rerunning the publisher against
canonical state; they are projection-owned, not pinned, and are never imported into the Git
registry.

### Unmatched / ambiguous states remain operational, not canonical

`canonical_object_map.status` in (`unmatched`, `ambiguous`) is review/workflow state — "this
legacy row has not been resolved yet" or "resolution is contested." The registry's `state`
vocabulary (`active` / `retired` only — see "Registry schema" below) makes it structurally
impossible to store an unresolved or contested mapping as if it were settled.

### Crosswalk overrides remain Mechanism-A matching inputs

`integration_data/crosswalk_overrides.json` continues to feed `tdr_bridge/release.py`'s matching
logic exactly as before. A reviewed override is a disambiguation hint for a derived,
recomputed-every-release mapping — not, by itself, a pinned canonical identity decision. All five
current override entries stay exactly where they are; a later packet may individually review and
promote specific ones into the registry if warranted, but none are auto-promoted here.

## Phase-E verification finding

Architecture review inspected `apply_vehicle_serving_projection` directly
(`supabase/migration_v14_serving_projection.sql`) and confirmed the RPC writes three kinds of
`canonical_object_map` rows automatically, every time it projects a model:

1. `source_table='models', canonical_entity_type='generation'` — one row per projected model,
   recording "this legacy model row represents this canonical generation in the serving layer."
2. `source_table='model_powertrains', canonical_entity_type='variant'` — one row per projected
   powertrain child.
3. `source_table='trims', canonical_entity_type='market_trim'` — one row per projected trim child.

All three `insert` blocks use the identical literal values:

```sql
status = 'verified',
match_basis = jsonb_build_object('basis','phase-e canonical serving projection','model',v_canonical_model),
verified_by = 'phase-e-publisher'
```

This is not a human decision recorded once — it is the publisher's own deterministic output,
re-written (`on conflict ... do update`) every time the projection runs. This directly confirms the
architecture review's finding: **`status = 'verified'` in `canonical_object_map` means "this
mapping is authoritative enough for the current operational bridge," not "a human reviewed and
pinned this identity."** The one row that genuinely represents a human review
(`e1a0b9fd-2d57-477d-b13f-1647d36d0298` → `jaecoo.jaecoo_5_ev`, `verified_by='OpenAI GPT-5.6
Sol'`, a detailed `match_basis` narrative rather than the fixed Phase-E literal) is
indistinguishable from the eight Phase-E rows by `status` alone — only `verified_by`/`match_basis`
tell them apart, and nothing enforced that distinction as a schema-level invariant before this
packet. This finding is exactly why the registry's `authority_basis` field exists as a first-class,
validated concept (see "Registry schema" below) instead of registry membership being inferred from
`canonical_object_map.status`.

Phase 1A's audit output is unaffected by this finding and unchanged in behavior — see "Relationship
to the Phase 1A contract" below.

## Why agreement is not enough

Mechanism A's release-build crosswalk agreeing with a canonical name, a canonical alias, or a
reviewed `crosswalk_overrides.json` entry is a **deterministic computation**, not a decision made
by inspecting the actual legacy row and the actual canonical entity side by side. Two failure
modes this distinction guards against:

- A future rename or alias collision could cause Mechanism A's derived match to silently point at
  a different canonical entity on the next release build — that is exactly the "derived" trust
  level's meaning (`EXTERNAL_IDENTITY_CONTRACT.md`), and exactly why a derived match must never
  become a pinned registry entry: the registry's whole purpose is to hold facts that do *not*
  silently change when the release rebuilds.
- Bulk-importing all 383 current Mechanism A links (or the 8 Phase-E rows, or the 326 unmatched
  rows) would immediately make the registry indistinguishable from a cache of Mechanism A/B's
  current state — defeating the point of introducing a registry at all. The registry stays small
  and honest by construction: it only grows when someone deliberately reviews and commits a new
  binding.

## Registry schema

Implemented in `automotive/vehicle_master/tdr_bridge/external_identity_registry.py`;
data lives in `automotive/vehicle_master/integration_data/external_identity_registry.json`.

```json
{
  "schema_version": 1,
  "bindings": [
    {
      "namespace": "legacy_tdr",
      "external_entity_type": "model",
      "external_id": "e1a0b9fd-2d57-477d-b13f-1647d36d0298",
      "canonical_entity_type": "model",
      "canonical_id": "jaecoo.jaecoo_5_ev",
      "state": "active",
      "authority_basis": "explicit_review",
      "verified_at": "2026-09-09T06:06:07.164815+00:00",
      "verified_by": "OpenAI GPT-5.6 Sol",
      "evidence": { "...": "..." },
      "notes": "...",
      "imported_at": "2026-09-15",
      "imported_by": "phase-1b-registry-seed"
    }
  ]
}
```

| Field | Required | Notes |
|---|---|---|
| `namespace` | yes | Only `legacy_tdr` today, matching `lib/external-identity/types.ts`'s `ExternalNamespace`. |
| `external_entity_type` | yes | `brand \| model \| model_powertrain \| trim` — matches the TS contract's normalized vocabulary exactly. |
| `external_id` | yes | For `legacy_tdr`, must be a syntactically valid UUID. |
| `canonical_entity_type` | yes | `brand \| model \| generation \| variant \| market_trim`. |
| `canonical_id` | yes | Must resolve to a real entity of the declared type in the canonical catalog — required for **both** `active` and `retired` bindings (see "Binding states" below). |
| `state` | yes | `active \| retired` only — see below. |
| `authority_basis` | yes | `explicit_review` only, in Phase 1B — see below. |
| `verified_at` / `verified_by` | optional | Original provenance, preserved verbatim from wherever the decision was first recorded — never rewritten to imply a different actor or method. |
| `evidence` | optional | Free-form object — whatever supports the decision. |
| `notes` | optional | Free text. |
| `imported_at` / `imported_by` | optional | The registry's **own** import metadata — distinct from `verified_at`/`verified_by`, which describe the original decision. Kept separate deliberately: a binding's original verification and its later import into this registry are different events with different actors. |

### Binding states

Deliberately narrower than Mechanism B's `status` column:

- **`active`** — the current pinned binding.
- **`retired`** — historically pinned, no longer current, `canonical_id` optionally retained for
  historical meaning (never required to be nulled out — see the "retired with contextual ID"
  concept in `EXTERNAL_IDENTITY_CONTRACT.md`, the same idea applied here).

**`unmatched` and `ambiguous` are never valid registry states.** Those are resolution/review
workflow states that belong to Mechanism B's operational bridge, not to canonical binding truth —
storing one here would make the registry indistinguishable from a review queue.

### Authority basis

At minimum the schema distinguishes an explicitly reviewed/pinned decision from anything derived
or projection-owned — and in Phase 1B, `explicit_review` is the **only** value the validator
accepts. `derived` and `projection_owned` are real, documented concepts (see the ownership table
above) but are deliberately **not** valid `authority_basis` values here: a record asserting either
would be a category error a schema-level reject prevents, not something to accept and merely
label. Those concepts belong in documentation and in Phase 1A's audit classifications, not as
seeded canonical registry records.

### Key and cardinality rules

The binding key is `(namespace, external_entity_type, external_id, canonical_entity_type)`. At
most one *current* binding may exist per key — enforced by the validator, not by a database
constraint (there is no database here). This deliberately **permits** one external legacy ID to
have bindings at multiple canonical target entity types (e.g. a legacy model row pinned as
evidence for both a canonical model and a canonical generation — different keys, not conflicts),
mirroring Phase 1A's comparability rule exactly.

**`canonical_object_map`'s global `unique (canonical_entity_type, canonical_id) where status =
'verified'` index is deliberately NOT carried over into this registry.** That index encodes "at
most one legacy source may claim to be verified-authoritative for a given canonical entity,"
which made sense for a single-namespace write-authority gate. The generic registry must be able to
represent multiple external identities — and, in the future, multiple namespaces — legitimately
pointing at the same canonical entity (two different legacy systems both correctly identifying the
same car, say). **External-key uniqueness matters; global canonical-target uniqueness is not a
generic registry invariant**, and the validator does not enforce it.

## Canonical target validation

Every `active` or `retired` binding's `canonical_id` must resolve to a real entity of the declared
`canonical_entity_type` in the canonical Vehicle Master catalog
(`vehreg.catalog.Catalog.{brands,models,generations,variants,trims}`). A type mismatch (the ID
exists, but as a different entity type) is reported distinctly from "does not exist at all," for a
more actionable error message. This validation is **entirely offline** — it loads the local
catalog from `vehreg/data/`, no Supabase read or credential required, and never checks whether the
corresponding legacy Supabase row still exists (that is explicitly a later reconciliation layer's
job, not this offline validator's — see "No source-of-truth loop" below).

The registry itself is year-independent — a pinned decision does not expire — but offline
canonical-target validation checks against one catalog year (by default
`vehreg.catalog.DEFAULT_YEAR`), since canonical IDs are stable and never recycled
(`INVARIANTS.md` rule 5): a target valid in the current year is the practical, available check.

## No source-of-truth loop

The target architecture must never create this cycle:

```
Git canonical registry → Supabase projection → read Supabase back → rewrite Git canonical registry
```

Git canonical truth must not depend on its own serving projection. A future Supabase projection of
this registry (not built in Phase 1B) must flow **one-way** from canonical Git state outward,
except for separately-reviewed commands entering through the existing canonical write/review
pipeline (`vehreg/canonical_write.py`, `docs/CANONICAL_INPUT.md`) — exactly the same rule that
already governs every other canonical fact in this repository. This registry's own offline
validator enforces this by construction: it reads the registry file and the local catalog only,
never Supabase, so there is no path by which a live read could feed back into what the validator
accepts as valid Git state.

## Relationship to the Phase 1A contract

`EXTERNAL_IDENTITY_CONTRACT.md`'s audit semantics are **unchanged** by this decision. The eight
Phase-E rows correctly remain `mappingState: "resolved"`, `trustLevel: "verified"` in Phase 1A's
audit output — that accurately describes `canonical_object_map`'s current *operational* state, and
Phase 1A's job is to observe that state honestly, not to decide what should own canonical truth.
Phase 1B does not change what Mechanism B's `status = 'verified'` *means* operationally; it adds
the previously-missing distinction between "operationally verified" and "canonically pinned" as a
**separate, additional** dimension, recorded in this new registry, not by retroactively
reinterpreting Mechanism B's status column or renaming any existing database value.

Concretely:

- `verified` in Mechanism B is, and remains, an operational status/trust statement about the
  current serving/write-gate bridge — not a claim about long-term persistence ownership.
- Provenance (`match_basis`, `verified_by`) can show that a `verified` mapping was either
  explicitly reviewed (free-text narrative, a named human/process) or generated deterministically
  by a publisher (`phase-e-publisher`, the fixed literal `match_basis.basis` string) — Phase 1B's
  registry decision is exactly about not conflating those two.
- Operational verification (Mechanism B) and canonical persistence ownership (the new registry)
  are separate questions, answered by separate, independently-maintained records.

No existing Mechanism-B database `status` value is renamed, and no Phase 1A TypeScript type,
classification, or test changes as a result of this packet.

## What Phase 1B deliberately does not do

- **No production consumer cutover.** `tdr_bridge/release.py`, `lib/canonical-write-shadow.ts`,
  `apply_vehicle_serving_projection`, `canonical_object_map`, the `current_vehicle_*` views,
  registration ingestion/analytics, ECO ingestion, canonical input commands, and every application
  page/compare/member-dashboard consumer are all unchanged. Nothing reads from the new registry in
  production.
- **No Supabase migration, write, or behavioral change.** No new table, RPC, or RLS policy; no
  write to `canonical_object_map`; no live Supabase read (the offline validator never connects to
  Supabase at all).
- **No retirement of `crosswalk_overrides.json`** or any existing Mechanism A/B path.
- **No bulk import** of Mechanism A's derived links, Mechanism B's unmatched rows, or the
  Phase-E projection-owned rows — see "Initial migration seed" below.

## Initial migration seed

Exactly **one** binding: the `legacy_tdr` model mapping `e1a0b9fd-2d57-477d-b13f-1647d36d0298` →
`jaecoo.jaecoo_5_ev`, `authority_basis: "explicit_review"`. This is the one row, out of the nine
currently `verified` `canonical_object_map` rows, whose provenance is an actual human/named review
(detailed `match_basis` narrative, `verified_by='OpenAI GPT-5.6 Sol'`, notes: "First deliberately
verified Phase C pilot") rather than the fixed `phase-e-publisher` literal the other eight carry.

**Explicitly excluded from this seed, and why:**

| Excluded | Count | Why |
|---|---:|---|
| Mechanism A derived Brand+Model links | 383 | Derived, recomputed every release — agreement with a name/alias/override is not a pinned decision. See "Why agreement is not enough." |
| Mechanism B `unmatched` model rows | 326 | Review/workflow state, not canonical binding truth — `unmatched` is not a valid registry `state`. |
| Phase-E projection-owned verified rows (1 generation + 3 variants + 4 market_trims) | 8 | Deterministically generated by `apply_vehicle_serving_projection`, reconstructible from canonical state + the publisher — see "Phase-E verification finding." Not a review; `verified_by='phase-e-publisher'` and the fixed `match_basis.basis` literal are the tell. |
| `crosswalk_overrides.json` entries | 5 | Reviewed *matching inputs* to Mechanism A, not pinned identity decisions in their own right. May be individually reviewed and promoted by a later packet. |
| Speculative ECO/DLT/OEM links, future namespaces | 0 | Not implemented — out of scope for this packet and for the registry's current single-namespace, single-source design. |
